# Known causes, and the skill that fixes each

Check each against the workflow files and the numbers from `measure.py split`.
A cause counts only when the numbers show it. "How to see it" names where
to look; a clue there is not yet the cause, so confirm it as the row says
before ranking it. The table says nothing about how common a cause is, so
check every row.
GitHub docs behind the rows marked so: `references/evidence.md`.

| # | Cause | How to see it | Fixed by |
|---|---|---|---|
| 1 | Dependency cache never saved on the default branch or the pull request's base branch, so a pull request's first run starts cold unless a run on its own branch or an earlier job saved one (a pull request's run can restore caches from its own branch, the default branch and its base branch, and saves only to its own merge ref: GitHub docs) | Cache step logs say "Cache not found" on most first runs of PRs; no cache-saving run on `main` or the base branch (`gh api repos/OWNER/NAME/actions/caches` lists each cache's ref) | ci-cache |
| 2 | Cache key misses the toolchain or tool version (Rust, sccache, Node, RUSTFLAGS), so the restore hits but may restore files the new version can't use (whether it can depends on the tool) | The restore step reports a hit while the compiler cache's own hit rate (sccache, ccache) is near 0%, or compile time on hit runs matches miss runs; key built from the lockfile alone. Confirm with the tool's own miss reasons where it gives them | ci-cache |
| 3 | Parallel jobs share one cache key (setup-go's docs warn of this for parallel builds), and the first job to save it wins, because a saved cache can't be changed (GitHub docs); it may hold only what that job built | Same key in several jobs; one job's setup or build much slower than the rest; confirm the same ref and paths, which job's save won, and what the others restored | ci-cache |
| 4 | The repository's cache size cap (10 GB unless raised) evicts the least recently used entries, so caches go cold (GitHub docs) | Total cache size near the cap (`gh api repos/OWNER/NAME/actions/cache/usage`) is a clue; a cache that was listed, is gone sooner than the retention period (7 days unless changed) after its last use, and misses after suggests eviction; a manual deletion looks the same, so it stays unconfirmed unless the reason is known | ci-cache |
| 5 | A cache that is slower than the work it saves (node_modules restore against a filtered install) | The whole setup on exact hits, partial hits and misses, weighted by how often each happens, against an uncached install (ci-cache step 3.5) | ci-cache |
| 6 | Many tiny jobs each pay the setup steps they run (checkout, toolchain, install) | Jobs whose running time is a small share of their total; count only setup steps each job really runs | ci-workflow |
| 7 | Superseded runs keep going after a newer push | No `concurrency` group; confirm with runs that were still running when a newer push to the same PR started (compare `created_at` with the older run's last job end) | ci-workflow |
| 8 | A `needs` edge A → B where B reads none of A's outputs and A gates nothing. Dropping it lets B be queued when its other needs end (or at the run's start): B becomes eligible up to end(A) minus the latest end of its other needs sooner, and the run ends sooner only where B's path decides the end, by at most the gap to the next path that doesn't pass through the edge | The link on the slowest path (`split`'s chains); then, in the workflow as it was in the runs, that B uses none of `needs.A.outputs`, `needs.A.result`, `toJSON(needs)`, an artifact or cache A saves, or anything A publishes, that its `if:` doesn't rely on A's success, and that A isn't a gate (a deploy after tests is one). Trace every job downstream of B too (on every event, push and release included): one that relied on A having passed before B, or on A's artifact, still needs A. Work out the saving per run from the job times | ci-workflow |
| 9 | Slow checkout (full history, large repository) | Checkout step seconds; `fetch-depth: 0` | ci-workflow |
| 10 | Tools compiled on every run that ship as prebuilt binaries | Long install steps running `cargo install`, `go install` and the like | ci-workflow |
| 11 | One or a few tests take most of the test step | Per-test times from the JUnit report | ci-slow-tests |
| 12 | Tests use fewer workers than the runner has cores, or reload modules per file (Vitest isolates each file by default) | Worker count against `nproc` (GitHub's standard Linux runner has 4 cores on public repositories, 2 on private ones); per-file setup time | ci-slow-tests |
| 13 | Shards that each pay a long setup | Setup share per shard | ci-slow-tests, ci-workflow |
| 14 | Real sleeps or real network calls in tests | `sleep(` in tests; tests that call a server | ci-slow-tests |
| 15 | Jobs that fail and then pass on a rerun of the same commit, or a test that fails alone on several pull requests: a pull request's own change fails it on that pull request, and a broken base fails every run until fixed, so failures on several pull requests, each with the test passing before and after it on that base, point to a cause outside those changes, or to each pull request having broken and then fixed it itself: a candidate to check, not a finding | `rerun_flakes` in the split; `measure.py flaky` over the runs' test reports, lined up per workflow file and base ("recurring": alone on 3 or more pull requests). Recurring is a candidate: read two or three of those pull requests to check they didn't change what the test covers (a snapshot test many changes break isn't flaky) | ci-flaky-tests |
| 16 | Retries, long timeouts or `continue-on-error` hiding failures | Grep the workflow and test config | ci-flaky-tests (find the cause), never by removing the check |
| 17 | Many pushes per pull request, with runs failing on format, lint or type errors | Pushes per PR; failed step names | ci-guard |
| 18 | A large share of minutes in runs that failed, timed out or were cancelled | The failed-or-cancelled share in the split; confirm by reading why they failed (a run that caught a real bug isn't waste) | ci-guard, ci-flaky-tests, ci-workflow (cancelled) |
| 19 | Long waits for a machine | Waiting share on the slowest path; check whether queued jobs hit the plan's concurrent-job limit (GitHub docs: 20 jobs and 5 macOS on Free), a `concurrency` group or a matrix `max-parallel`, and whether the runner label has machines | ci-workflow when one of those is the limit (fewer or folded jobs, cancelled superseded runs); moving jobs to another runner, macOS off especially, is for a person, since it can drop platform coverage; otherwise a person, since runner size or a provider costs money |
| 20 | Path filters on a workflow behind a required check (the check stays pending forever) | `paths:` on a workflow whose job is required | ci-workflow (review only) |
| 21 | Catch-up runs: pull requests merged with main again and again, by people or by agents running `gh pr update-branch`; the split counts merge commits and can't tell an update a conflict needed from one only to stay current, so read a sample of them; check whether branch protection requires branches to be up to date | The `catch-up runs` line in the split; `strict: true` in `gh api repos/OWNER/NAME/branches/BRANCH/protection/required_status_checks` | ci-guard (the agent rule); a person (a merge queue in place of the up-to-date rule) |
| 22 | No cache at all for dependencies or build outputs | Install or compile steps take minutes, no cache step exists, and the setup actions cache nothing: their own `cache` inputs are off and nothing turns caching on implicitly: `actions/setup-node` from v5 caches with no `cache` input when `package.json`'s `packageManager` names npm, yarn or pnpm with a version (`npm@10.8.2`; from v6, npm only, via `packageManager` or `devEngines.packageManager`), unless `package-manager-cache: false`; a lockfile alone doesn't, and v4 and earlier never do (setup-node README and source); `gradle/actions/setup-gradle` has no `cache` input and caches by default (its own log lines aren't read by `cachelog`; its job summary says what it restored). Read the version the workflow pins. Before ranking it, read the setup step's log for a cache restore or save line (`measure.py cachelog`): one there means a cache exists, and the cause is another. On a self-hosted runner that persists between jobs, fast installs with no restore line can be the runner's own warm package cache (`~/.npm`, a pnpm store) rather than any cache step or implicit setup-action cache: read `runs-on` before crediting either, and note that an ephemeral runner starts cold | ci-cache (for Gradle or Maven, its `references/jvm.md`) |
| 23 | Docker images rebuilt from scratch on every run | `docker build` or `docker/build-push-action` with no `cache-from`, and build logs showing layers rebuilt (a builder that keeps a local cache may not need one); the build step's seconds | ci-cache |
| 24 | A hung job runs until GitHub's default `timeout-minutes` of 360 (GitHub docs) | Jobs with no `timeout-minutes`; failed or cancelled jobs far longer than the median. A step with no output for most of its time, then a timeout or cancellation, is a suspected hang (a slow, silent compile looks the same); a progress signal or a reproduction tells them apart | ci-workflow |
| 25 | One shard finishes well after the others | Per-shard running time from the split; per-file test time from the report | ci-slow-tests |
| 26 | Independent steps run one after another in the job that finishes last. With both halves running at once, the job takes as long as the longer: run side by side in the same job (native `parallel` steps), it saves up to min(moved, kept) seconds, less where they compete for the runner's cores, memory or disk (two memory-heavy steps can be slower together); moved to a new job with the same `needs` (for a person: it adds a runner and minutes and changes the job graph), it saves min(moved, kept − d) a run, where d is how much longer the new job waits, sets up and cleans up than the old (negative, a slowdown, when d exceeds the kept time), and its minutes change by both jobs' new billed durations against the old job's; on a pool with no free runner the kept job can queue behind the new one, so compare both new finishes with the old | `split`'s steps of the last job that did work: two or more long steps that aren't setup, next to each other (a step between them, such as one that writes `$GITHUB_ENV`, can change what the later one tests) (a job whose steps overlap already runs them side by side); then, in the workflow, that neither group reads or writes files, outputs, `$GITHUB_ENV`, a database, services or ports the other uses, or relies on its cleanup | ci-workflow |
| 27 | Gate jobs at the end of the slowest path (a called workflow's final check job, then the caller's), each paying its own queue, setup and gap before it for a second of work | `split`'s candidate gates (trailing jobs whose steps, besides the runner's own set-up and clean-up, ran under 5 s) and how much sooner each run would end without them, every other job ending when it did: a gate a required check needs stays and adds its time back, and removing a gate that other jobs need lets them start sooner, which that figure doesn't count (work it out from the `needs:` graph). Confirm each in the workflow: a 2-second policy check looks the same | ci-workflow |

Items for a person, never fixed by a skill: bigger or different runners, new
providers or paid services, and repository settings such as a merge queue.
No skill runs fewer tests before a merge.
